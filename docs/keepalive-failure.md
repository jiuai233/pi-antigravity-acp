# AGY ACP 保活失败复盘

> **结论先行：** AGY 1.5.7 的单字节影子修改取消了 `sendPing` 对首个 input-only 响应的提前返回，但没有取得缓存收益。两次基线和改后唯一保活针的最终缓存读数均为 0；随后没有第二针。约 600 秒后的真实请求仍为 0 缓存。因此这轮不能证明已有热缓存是否能续期，也不支持发布新的保活配方。本文只总结冻结证据，不建议或执行任何在线重测。

## 结论：这轮失败在哪

实验没有建立可用于检验续期的**正缓存基线**：WARM1、WARM2、唯一保活针、POST_10MIN 的缓存读数全为 0。单改早停分支之后，后台针完整收到 HTTP 200、`MAX_TOKENS` 终态并正常结束，最终缓存仍为 0；实验期间只观察到这一针，尽管观察窗口越过了原本可能出现第二针的时间。故本轮证明的是“这项单变量改动没有在该冷基线样本中观察到缓存收益”，不是“热缓存必然不能续期”，也不是“已成功续期”。

首针 input-only 早停不是完整解释：改后针已有完整终态，最终仍无缓存字段（完整 protobuf 的缺省缓存计数按零值记录）。原始 EOF／错误处理和低命中保护仍在；没有运行时分支轨迹证明具体哪条删表路径实际执行。不要盲删保护，也不要把间隔从 270 秒改为 240 秒当作已解决问题。

实验记录与独立复核结论一致；复核通过的是证据与结论边界，不是热缓存续期方案。影子修改未写入生产二进制，原代理配置及其它工作区改动未修改。历史依据：`notes/verify/agy-keepalive-shadow-20261113.md`、`notes/verify/agy-keepalive-shadow-sol-20261113.md`。

## 原始客户端机制与单字节影子修改

只读字节检查记录了 AGY 1.5.7 原件身份及相关代码路径（完整字节证据见随包 `../evidence/keepalive/`）：

| 位置 | 原始字节／含义 |
| --- | --- |
| offset `52283296` | `b806000000c3`：固定返回 6（最大针数） |
| offset `52288359` / VA `0x1431de567` | `74aa`：`sendPing` 的早停分支；原始行为可在首包已有缓存计数，或缓存为零但 input 非零时提前返回 usage |
| offset `52287395` / VA `0x1431de1a3` | `0f86c1000000`：cacheRead 与 input 比较后转入低命中删表路径的保护 |
| offset `52287350` / VA `0x1431de176` | `0f852a010000`：真实错误的另一删表路径 |
| offset `52285908` | `000c41dd3e000000`：270 秒间隔立即数 |

影子副本只把 offset `52288359` 的一个字节从 `74aa` 改为 `ebaa`，使该路径不再在首个 input-only 包处早停。manifest 记录原件 SHA256 `a30f863bc4f2c27f913e212e3eea13ebf57f181a8bfbcd1fada4d00da3e63444`、影子 SHA256 `150e8564514c97e053100bd30434fe6216ad7908088170c409e38e5d2660a93d`，其余上述 guard、270 秒立即数及 6 针上限保持不变。

这只是客户端单字节影子改动；它没有删去 EOF／真实错误或低命中处理，也没有证明服务端保留缓存。保活身份应以请求中的 `labels.prompt_cache_keep_alive="true"` 与 `maxOutputTokens=1` 确认；生产观察器的 `class=unknown` 识别不了这次请求中的标签位置，不可据此否认保活针身份。

## 为什么不能证明热缓存续期

1. **没有热缓存起点。** 两次基线的缓存均为 0；无正缓存读数可供前后比较。
2. **改后针仍然零缓存。** 它不是因首包提前中止而缺少尾部观测的样本：完整流已有 `MAX_TOKENS` 终态且成功结束，最终缓存仍为 0。
3. **没有第二针。** 空闲窗口超过预期第二周期，不等于第二针已成功发出；记录中只有一针。
4. **请求不构成严格 TTL 对照。** 保活针与 WARM2 前两个消息相同，但末条消息指纹不同，`generationConfig` 和 `labels` 也改变。不能当作与真实请求逐字节相同的后端对照。
5. **机制路径未归因。** EOF／错误和低命中删表保护仍存在且与停止续调度相容，但网络证据无法判定实际执行了哪个分支。

所以，观察结果不能确认热缓存续期成功，也不能外推为所有既有热缓存都无法续期。

## 确认、推断、未知的分离

**确认（冻结记录直接支持）**
- 单字节改动位置、改前改后字节、影子/原件哈希及未改的保护位置，由 `manifest.json` 记录。
- 只有一个身份明确的后台保活针；该针完整结束、`MAX_TOKENS`、缓存读数 0。WARM1、WARM2、POST_10MIN 也均为 0 缓存。
- 一共五条模型生成请求，包含一次自动 Flash-lite checkpoint；最终公开 usage 合计输入 273,956、缓存 0、输出 87、思考 135。
- 请求间隔及只有一针、后台没有增加业务回合的观察，见冻结轨迹与复核报告。
- 用户特别关注“反复真实请求 + 自建正向代理可能改变客户端指纹”这一封号怀疑。**这是重点风险提示，不是已证实的官方封号原因。** 现有 403／停用信息没有给出具体命中信号。

**推断（与证据相容，但非直接分支证明）**
- 零热基线使本轮不具备裁决“已有缓存续期”的条件。
- EOF／错误和低命中保护仍在，可能与未继续调度相容；实际命中哪个分支未知。

**未知／未验证**
- 一个稳定、逐字节相同的正缓存前缀能否在保活后续期；成功第二针能否带来后续真实请求缓存命中。
- 这轮停止续针的具体运行时代码分支；服务端缓存 TTL 与相关后端条件。
- 代理指纹变化或反复请求是否导致账号受限；现有证据不能确立因果。

## 接手建议：离线复算而非重复线上探针

- 先使用随包安全证据和 `analyze.py` 离线复算：核对最终 usage（不要累加逐包快照）、请求身份、时间窗、影子字节差异与保护字节。冻结 JSONL 的内容不含提示正文、响应正文或认证头。
- 复用包内源码入口、脱敏轨迹和已有离线测试；在假 ACP／本地 mock 中验证客户端状态机，不发送真实模型请求，不扫描或循环探测端口。
- **不要自动反复打 AGY／Google 真实接口或会转发真实请求的端口；不要为了本问题另搭正向 TLS 解密抓包代理。** 代理指纹差异与反复请求是用户明确点出的封号重点怀疑，但因果尚未证实。该约束不要求擅自移除正常联网所需的既有代理。
- 不要盲目删除真实错误／低命中保护；不要把 270 秒改 240 秒或打满针数冒称解决。若未来另获明确授权要做新实验，先具备正缓存基线、明确最小问题和授权，并设计可观察第二针及真实请求命中的判据；本复盘不授权该实验。
