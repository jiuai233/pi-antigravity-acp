# 开发接手前：务必不要重演的在线诊断

## 先遵守这三条

1. **不要反复打 AGY／Google 服务接口，或为了诊断循环请求端口。** 不运行批量生成、额度轮询、并发在线探针或自动“试到成功”；本地端口会转发真实业务请求时同样适用。先用已有错误、冻结轨迹和离线测试。
2. **不要为接手排查另搭正向代理，尤其是解密 TLS 后重新建立上游连接的抓包／中间人代理。** 不复制历史观察器，不擅自注入代理URL、CA或改写原生请求。这里限制新增诊断链路，不要求删除正常联网所需的既有代理。
3. **遇到 429、403 或账号验证要求，停止诊断探针和其自动重试。** 保存已有错误与脱敏日志；不要靠换身份提示、换账号或反复请求判断“是否恢复”。

接手包本身不授权在线实验。确有必要时先写清需要回答的具体问题、已有证据、最小动作和账号授权，由使用者决定；不把一次授权扩大成连续轮询或抓包实验。

## 封号原因应怎样表述

**“反复请求＋自建正向代理，可能因请求行为及客户端指纹差异触发风控”是原使用者目前最主要的封号怀疑，也是本包必须保留的接手提醒。**

历史上确实使用过本机正向观察代理，也确实出现过多次429自动重试；原生日志另有403／PERMISSION_DENIED，并提示服务因ToS停用。服务端没有给出具体命中信号。不能把“代理指纹导致封号”写成已经查实或官方确认的原因。

技术上，TLS解密再转发的代理可能改变上游可见的TLS／HTTP客户端特征，具体取决于实现；现有证据未完成封号前后指纹的对照证明。不要为了补这个证明重新搭代理、拿真实账号重复实验。

身份提示与429的对照是另一条证据，不能用它解释403停用，也不能据此宣称停用账号已恢复。

## 验证边界

- `plugin/test/`：假 ACP／回环 MCP／合成历史与媒体离线单测。
- 端口相关排障先查进程归属、监听信息和已有日志，不向业务接口循环发送请求。
- 现有源码保留 `plugin/src/network-monitor.ts`；插件本身不附带观察器，也不启用抓包代理。
